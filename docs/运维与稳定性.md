# 运维与稳定性手册

面向本系统的日常运行、故障排查与参数调优。全部内容基于本机实测记录。

---

## 一、根因回顾(历史故障与修复)

系统早期出现过"Ollama 无响应 → 网页崩溃",根因是多层问题叠加,均已修复:

| # | 根因 | 后果 | 修复 |
|---|---|---|---|
| 1 | 后端以会话任务方式启动,无守护 | 进程被回收即 8000 消失,页面全挂 | `scripts/run_server.ps1` 守护:后端崩溃 5 秒自动重启;Ollama 宕机自动唤醒 |
| 2 | 8.9GB 大模型逼近 8GB 显存 | 加载慢、偶发 OOM → 长时间无响应 | 换 `deepseek-r1:7b`(4.7GB);限制同时加载模型数 |
| 3 | 无并发闸:嵌入/生成可同时打 Ollama | 显存挤爆、请求互相饿死 | 客户端全局信号量:同时仅 1 个嵌入批次 + 1 个对话流 |
| 4 | `async def` 端点内做阻塞 IO | 单个请求卡死整个事件循环 | 重 IO 端点全部改为同步 `def`(FastAPI 自动放线程池) |
| 5 | 前端 SSE 无超时 | Ollama 一卡页面无限挂起 | 10 分钟总超时 + 90 秒空闲看门狗自动中断;提供「停止」按钮 |
| 6 | 无请求超时与熔断 | 连接悬死无提示 | Ollama 调用带连接/读取超时;`/api/qa` 前置探活快速返回友好错误 |

## 二、正确启动方式

```bat
start.bat
```

执行内容:
1. 首次写入 `OLLAMA_MAX_LOADED_MODELS=2`、`OLLAMA_KEEP_ALIVE=10m`(用户级环境变量);
2. 拉起 Ollama(未运行/僵死时),校验模型,缺失时提示 `ollama pull`;
3. 启动后端守护循环:健康检查每 5 秒;进程崩溃自动重启;Ollama 失联自动唤醒;
4. 日志实时落盘 `data/logs/`:`backend.out.log` / `backend.err.log` / `guard.log`。

关闭方式:守护窗口 `Ctrl+C`。**若 8000 端口已有健康后端在跑,守护会接管监视而非抢端口。**

仅调试用(无守护):

```bat
cd backend
.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

## 四、常见问题处理

### 4.1 页面提示"模型未就绪 / Ollama 未连接"
打开 Ollama 应用或运行 `ollama serve`;确认模型存在:`ollama list`(需 `deepseek-r1:7b` 与 `bge-m3`);
守护窗口会每 10 秒自动尝试唤醒 Ollama,无需手动重启后端。

### 4.2 提问卡住 / 一直"思考中"
冷启动加载模型需要时间(首次约 10–30 秒,之后 10 分钟内常驻);前端 90 秒无增量会自动中断并提示。
若频繁中断:检查显存与 CPU 占用,注意 GPU 满载属正常,等待即可;并发提问会排队(全局串行),属预期行为。

### 4.3 换用更大的模型
写入 `data/config.json`:`{"chat_model": "deepseek-v2:latest"}`,重启 `start.bat`。
注意 8GB 显存下 8.9GB 模型超限,加载慢、OOM 风险高,不推荐。

### 4.4 想彻底停止系统
守护窗口 `Ctrl+C`;Ollama 为托盘应用,可右键退出。系统未注册开机自启,每次开机后双击 `start.bat` 即可。

### 4.5 数据备份与迁移
整个 `data/` 目录即全部数据(SQLite + 每库独立向量目录 + 原文归档 + 日志),拷贝即备份/迁移。

### 4.6 审计日志增长过快
```bat
sqlite3 data\meta.db "DELETE FROM audit_log WHERE created_at < '2026-01-01'"
```

## 七、三项核心创新的运维要点

### 7.1 向量硬隔离
数据布局 `data/vectors/<kb_id>/chroma.sqlite3`(每库一个独立 Chroma 实例)。
删库即物理删除该目录;若被占用会改名 `.trash_<kb_id>_<时间戳>` 并在下次启动自动清理。
旧版单实例布局启动时自动迁移并校验数量,旧目录改名为 `data/chroma_legacy_backup` 可回滚。
查看证据:系统状态页「向量硬隔离证据」表,或 `GET /api/system/isolation`。

### 7.2 增量更新与精准删除
更新时按块内容哈希比对,未变更块复用向量;更新弹窗显示复用块数/耗时对比。
累计收益见系统状态页或 `GET /api/system/update-stats`。
删除返回 `zero_residue: true` 表示二次校验零残留;「对账清理」可随时兜底。

### 7.3 跨知识库冲突检测
每次问答会在最相关的多个知识库中比对,发现矛盾时:界面显示冲突面板;回答被约束为分列来源、提示冲突。
手动指定知识库模式同样参与跨库检测。检测耗时约 5–15 秒(与片段对数量相关)。
如嫌慢:调小 `conflict_pairs_limit`(如 3)或设 `enable_conflict_check=false`。
独立检测:`POST /api/qa/conflict-check {"question": "...", "kb_ids": [...]}`。

## 九、检索调优与评测

**检索链路**:向量通道(余弦)+ 词法通道(BM25:中文二元组 + ASCII 词)→ RRF 融合 →
确定性元数据重排 → 门槛判定(排序分与门槛分分离)。

**评测用法**:

```bat
cd backend
.venv\Scripts\python.exe ..\scripts\eval_retrieval.py
```

输出:四种检索模式(vector / lexical / hybrid / hybrid_rerank)的 hit@1、hit@3、MRR 消融表,
以及答案质量指标(引用命中率 / 事实命中率 / 拒答正确率)+ 证据 JSON(`scripts/_eval_result.json`)。

**调参经验**:
- 该拒答的没拒答 → 提高 `score_threshold`;
- 回答"资料未提及"但资料里其实有 → 降低 `context_min_score` 或提高 `max_chunks_per_doc`;
- 编号类问题命中不准 → 提高 `meta_boost_docno`;
- 多份相近制度被混答 → 已内置「★最相关来源」与多来源辨析提示,可提高 `meta_boost_docno` 进一步强化。
